Sources & disclaimer

Nobody published the manual, so the mods became the manual.

Magic Garden ships a real-time API for its own client — a WebSocket protocol for game actions, a Pixi.js scene graph for rendering, and a jotai atom store underneath the React UI. None of it is documented anywhere the game itself links to. This guide reconstructs it from three independent, open-source projects that each had to answer the same questions from scratch: what does a legal message look like, when does the server reject one, and how do you draw something into a canvas you don't own.

Where the three projects agree, that's a strong signal the behavior is real and not an implementation quirk of one mod. Where they diverge, this guide says so explicitly instead of picking a winner.

Ariedam64/MG-AriesMod — browser userscript Liam0306dis/garden-companion — browser userscript Ariedam64/mg-afk-android — native Android client mg-tokyo/QPM-GR — browser userscript ("Quinoa Pet Manager") Ariedam64/Magic-Garden-API — unofficial REST wrapper (asset/data mirror, not covered below)

00How the pieces fit

Everything the game does at runtime runs through one of three layers, and every mod hooks in at a different point:

1. The wire — a single WebSocket

One socket per room, carrying newline-free JSON text frames both ways. This is the layer that mg-afk-android speaks natively (it opens the socket itself, with no browser or game client involved at all) — which is why it's the cleanest source for the exact wire format.

2. The state store — jotai atoms

The React UI reads and writes a jotai atom graph. The atoms aren't just derived from the socket — some of them (which modal is open, whether the camera is in "cinematic" mode) are pure client UI state with no server round-trip at all. garden-companion hooks this layer directly instead of going through the socket for those.

3. The renderer — a Pixi.js scene graph

Tiles, sprites, the info-card tooltip, and player avatars are all Pixi display objects under one stage. MG-AriesMod reaches into this directly to draw its own text and badges as real children of the game's own nodes, rather than overlaying HTML on top of the canvas.

4. The userscript host

Both browser mods run as Tampermonkey userscripts injected into magicgarden.gg. That matters for one subtle reason covered below: a userscript sandbox has its own window, separate from the page's real one, so timers and globals have to be bound to the page's window explicitly or they silently misbehave.

The game calls its own engine/session scope "Quinoa" internally — it shows up verbatim in the scope path of every game message (["Room","Quinoa"]) and as the default gameName sent when voting for a game. That's where this guide's title comes from.

01Opening the socket

A room connection is a single wss:// URL. Every value in the query string is JSON-encoded — including plain strings, which arrive quoted ("web", not web). This mirrors exactly what the real client sends, string quoting included. 

url shapewss://magicgarden.gg/version/<gameVersion>/api/rooms/<roomId>/connect
  ?surface="web"
  &platform="desktop"
  &version="<gameVersion>"
  &capabilities="fbo_mipmap_unsupported"
  &locale="en"
  &clientDocumentId="<uuid>"
  &clientConnectionAttempt=1
  &clientNavigationType="navigate"
  &clientVisibilityState="visible"
ParamMeaning
gameVersionThe client build hash currently deployed (e.g. db34dc9). Connecting with a stale one gets you closed with code 4710 ("Version Expired") — re-fetch the current version before reconnecting.
roomIdLowercase alphanumeric room slug. Omit it (or generate a fresh random one) to get a private room of your own.
clientDocumentIdA UUID that identifies this "tab" for the whole session. Stable across reconnect attempts; regenerate only for a brand-new session.
clientConnectionAttempt1 for the first connection with this clientDocumentId, incrementing by one on every retry.
clientNavigationType"navigate" on the first attempt, "reload" on every retry.
reclaimSupersededSessionSend as literal true only when the previous connection was closed with a superseded code (4250/4300) and you're reconnecting the same identity. Omit entirely otherwise — don't send false.

Two ways to authenticate, both set at connect time — there's no separate login message:

Authenticated (Discord account)

Send a Cookie header carrying mc_jwt=<token>. The token comes from the Discord OAuth2 flow the game itself uses; nothing here mints one for you. No player id goes in the URL — the server assigns it and reports it back in Welcome.selfPlayerId.

Guest (anonymous)

Skip the cookie and instead pass an anonymousUserStyle query param: a JSON object with name, color, and the three avatar layer ids (avatarBottom/avatarMid/avatarTop) plus avatarExpression. The server assigns a temporary identity from that.

Also set a normal-looking Origin header (https://<host>) and a real desktop-Chrome User-Agent — consistent with platform="desktop" in the query string, in case anything server-side cross-checks the two.

typescriptfunction buildConnectUrl(opts: {
  host: string; version: string; room: string;
  documentId: string; connectionAttempt: number;
  isReload: boolean; reclaimSuperseded?: boolean;
}): string {
  const u = new URL(`wss://${opts.host}/version/${opts.version}/api/rooms/${opts.room}/connect`);
  u.searchParams.set("surface", '"web"');
  u.searchParams.set("platform", '"desktop"');
  u.searchParams.set("version", `"${opts.version}"`);
  u.searchParams.set("capabilities", '"fbo_mipmap_unsupported"');
  u.searchParams.set("locale", '"en"');
  if (opts.reclaimSuperseded) u.searchParams.set("reclaimSupersededSession", "true");
  u.searchParams.set("clientDocumentId", `"${opts.documentId}"`);
  u.searchParams.set("clientConnectionAttempt", String(opts.connectionAttempt));
  u.searchParams.set("clientNavigationType", opts.isReload ? '"reload"' : '"navigate"');
  u.searchParams.set("clientVisibilityState", '"visible"');
  return u.toString();
}

02Handshake sequence

client opens wss:// connection ──▶ server client on open, sends: { scopePath: ["Room"], type: "VoteForGame", gameName: "Quinoa" } { scopePath: ["Room"], type: "SetSelectedGame", gameName: "Quinoa" } ──▶ server server replies: { type: "Welcome", selfPlayerId, executedCommandSequence, fullState } ◀── client client seed local command-sequence counter from executedCommandSequence + 1 client connection is now "welcomed" — safe to send gameplay commands

Nothing else needs to happen before Welcome arrives — don't send gameplay commands before it, since the command-sequence counter isn't seeded yet and every one would be rejected as invalid_sequence.

After the handshake, the server also sends application-level text pings as the bare string "ping" (not a WebSocket protocol ping). Reply with the bare string "pong", verbatim, no JSON wrapper. Miss enough of these and the server drops you with close code 4400 after roughly 30 seconds of silence. 

typescriptsocket.addEventListener("message", (ev) => {
  if (ev.data === "ping" || ev.data === '"ping"') {
    socket.send("pong");
    return;
  }
  const msg = JSON.parse(ev.data);
  // ... dispatch by msg.type, see "Server → client" below
});

03Close codes & reconnecting

All three projects treat close codes above 4000 as application-defined. Codes agreed on by more than one project:

CodeMeaningReconnect?
4250Session superseded (heartbeat-based supersession)Yes — pass reclaimSupersededSession=true
4300Session superseded by a newer connection for the same identity ("newer user session")Yes — same as above; check the reason string doesn't say heartbeat before treating it as a real supersede
4400Idle timeout — you stopped answering application pings (~30s)Yes, immediately
4710Version expired — the client build you connected with is staleYes, but re-fetch the current gameVersion first or you'll just get closed again
4800Auth failed — bad/expired mc_jwt cookie, or a player record was found with none of the expected identity fieldsBounded retries only (don't hammer a bad cookie forever)
4100 / 4200 / 4310 / 4500 / 4700Other server-defined close reasons, not otherwise documented by any of the three projectsTreated as reconnect-worthy by default

Backoff shape that all three broadly agree on:

  • Exponential backoff from a small base delay (~1.5s), doubling per attempt, capped around 60s, plus random jitter so many clients don't retry in lockstep.
  • Superseded closes get a longer base delay before the first retry (on the order of 30s) since retrying instantly just gets superseded again.
  • The very first connection attempt of a brand-new session gets a handful of fast retries with no backoff, on the theory that an immediate failure is more likely a cold-start race than a real outage.
  • Re-seed clientConnectionAttempt from the retry counter and set clientNavigationType="reload" on every retry.
  • Re-fetch the current game version before reconnecting — the version changing out from under a long retry loop is exactly the case that produces an endless 4710 loop otherwise.

A message type called RoomFrame exists as a newer replacement for PartialState: same patch payload, just nested one level deeper (msg.state.patches instead of msg.patches). If you only implement one, implement PartialState and normalize any incoming RoomFrame into that shape — the server appears to be migrating between the two mid-rollout, and code that only understands one silently stops receiving state updates on the other.

04A friendlier hook point: MagicCircle_RoomConnection

Everything in the previous two sections is what you need if you're writing a standalone client with no browser involved — which is exactly mg-afk-android's situation. If you're a userscript running inside the real page instead, the game hands you something considerably friendlier: a single object, window.MagicCircle_RoomConnection, that wraps the raw socket and already does the JSON parsing, patch delivery, and Welcome bookkeeping for you. 

typescript — the shape worth knowinginterface RoomConnection {
  sendMessage(payload: unknown): void;
  // Immediate, synchronous send — returns false (and drops the message) if
  // disconnected or before Welcome. QuinoaCommand envelopes need this one:
  // sendMessage() queues instead, which hands a now-invalid sequence number
  // to a session that hasn't opened yet.
  trySendMessageNow?(payload: unknown): boolean;
  isCommandSessionReady?: boolean;

  // Fires (patches, fullState) on every state update. Newer bundles return
  // { currentState, unsubscribe } instead of a bare unsubscribe function —
  // handle both shapes.
  subscribeToPatches?(cb: (patches: unknown, fullState: unknown) => void): unknown;
  // Fires on initial connect AND every reconnect — replaces listening for a
  // raw "Welcome" message type by hand. Fires immediately with the current
  // state if you subscribe after the fact.
  subscribeToWelcome?(cb: (state: unknown, publishedAtServerMs?: number, executedCommandSequence?: number) => void): unknown;
  // Fires on every RoomFrame — the modern PartialState successor.
  subscribeToRoomFrames?(cb: (frame: { executedCommandSequence?: number; state?: { patches?: unknown } }) => void): unknown;

  // One-shot synchronous reads, no subscription needed:
  lastDistributedRoomPublication?: { executedCommandSequence?: number };
  lastRoomStateJsonable?: unknown;
}

function getRoomConnection(): RoomConnection | null {
  return (window as any).MagicCircle_RoomConnection ?? null;
}

Why reach for this instead of the raw socket, when you're already inside the page:

  • No manual JSON parsing or ping/pong handling — those live below this layer.
  • The command-sequence frontier is already tracked for you, at lastDistributedRoomPublication.executedCommandSequence, and kept current on every frame — no need to watch Welcome/RoomFrame yourself just to seed a counter (see Command sequencing).
  • Reconnects are transparent — subscribeToWelcome fires again automatically; you don't have to detect a new socket object.
  • State reads have a synchronous escape hatch — lastRoomStateJsonable for a one-shot snapshot when a full subscription is overkill.

This object's exact shape has moved between game builds — subscribeToPatches's return value alone has been observed as both a bare function and a { currentState, unsubscribe } record across bundles. Treat every field here as present-but-possibly-renamed, feature-detect before relying on any one of them, and keep a raw-socket fallback path (the previous two sections) for whichever piece your current target build doesn't expose.

This is also the natural place to intercept outgoing traffic if you're building a userscript feature that needs to observe or block specific commands — wrap sendMessage and trySendMessageNow the same way you'd wrap WebSocket.prototype.send, just one layer higher and already speaking parsed objects instead of JSON strings. See Multi-mod collisions for how to do that wrapping without stepping on another script doing the same thing.

05Flat messages vs. the QuinoaCommand envelope

Every outbound message carries a scopePath array that tells the server which subsystem it's for:

  • ["Room"] — room-level actions: chat, emotes, kicking, voting for a game, editing your own player record.
  • ["Room","Quinoa"] — gameplay actions inside the farming minigame itself.

Room-scoped messages are always sent flat: { scopePath, type, ...params }. Most gameplay actions, however, must be wrapped in a command envelope — the server is mid-migration from flat gameplay messages to this envelope, and a growing allowlist of action types get rejected outright if you send them flat.

flat Room-scoped, always

{
  "scopePath": ["Room"],
  "type": "Chat",
  "message": "hi!"
}

wrapped Gameplay command

{
  "scopePath": ["Room","Quinoa"],
  "type": "QuinoaCommand",
  "requestId": "<uuid>",
  "commandSequence": 42,
  "command": {
    "type": "HarvestCrop",
    "slot": 3,
    "cropItemId": "<uuid>"
  }
}

Sending a command-envelope type flat doesn't error loudly — it comes back as {"type":"QuinoaCommandResult","commandType":"unknown","ok":false,"code":"invalid_message"}, and the action just silently never happens. This is the single most common way a hand-rolled client "does nothing" for no visible reason.

Every action documented in the reference table below is tagged with which form it needs, but the underlying rule is a moving target: as the developers migrate more action types into the envelope, anything still marked flat today may need to move to wrapped in a future client build. All three projects derive this list empirically from the live client bundle rather than from any spec, and recommend the same fallback if an action you're sending starts silently failing: try wrapping it.

As of the client builds these mods target, the following stay flat even inside the Quinoa scope:

Ping, PlayerPosition, Teleport, SetSelectedItem, CheckWeatherStatus,
CheckFriendBonus, ThrowSnowball, QuinoaTutorialSkipped, RequestPetGreet,
DropObject, PickupObject, UpgradePetHutch, UpgradeSeedSilo,
UpgradeDecorShed, UpgradeToolShack

Ping and PlayerPosition aren't just "not migrated yet" — they're structurally different from a command. Ping gets a direct Pong reply rather than a QuinoaCommandResult, and PlayerPosition feeds a continuous movement-snapshot channel rather than a discrete, sequenced action. Neither is ever expected to move into the envelope.

06Command sequencing

The server numbers commands per connection. Welcome.executedCommandSequence is the last command number the server has executed; the next one you send must be that value plus exactly one. The sequence has to stay perfectly contiguous:

  • A duplicate or stale number is silently dropped — no result at all.
  • A gap (skipping a number) comes back as {"ok":false,"code":"invalid_sequence"} — and critically, every command after the gap fails the same way, because the gap never closes on its own.
  • A missing commandSequence field entirely is rejected as invalid_message, same as sending a command type flat.
typescript// Minimal correct sequencer
class CommandSequencer {
  private next = 1;
  // Call this for every incoming "Welcome" — including on reconnect.
  seed(executedCommandSequence: number) {
    this.next = executedCommandSequence + 1;
  }
  // Call this once per command you are about to send, right before sending it.
  take(): number {
    return this.next++;
  }
}

If you're sharing the socket with the game's own client (i.e. you're a browser userscript, not a standalone client), there's a second problem: the game keeps its own module-private counter that has no idea your commands exist. The moment you inject one command, your counter and the game's have both claimed the same next number for different things. See Multi-mod collisions for how the three projects each solve this — the short version is that a userscript must intercept and renumber the game's own outgoing frames too, not just its own.

A single fresh UUID (crypto.randomUUID()) goes in requestId on every envelope — used only to correlate a later QuinoaCommandResult back to the command that caused it, and, for userscripts, to recognize "this was one of ours" when it echoes back through the send-hook.

07Welcome

The first message after connecting. Shape (trimmed to what matters):

{
  "type": "Welcome",
  "selfPlayerId": "p_...",
  "executedCommandSequence": 17,
  "fullState": {
    "data": { /* room state: players[], chat, hostPlayerId, ... */ },
    "child": { "data": { /* game state: userSlots[], weather, shops, ... */ } }
  }
}
  • selfPlayerId is your player id for this session. The server assigns it — the connect URL never carries a client-chosen player id, and code that assumes otherwise will never find itself in fullState.data.players.
  • Room state (players, chat log, host) lives at fullState.data.
  • Game/farm state (garden tiles, inventory, shops, weather) lives one level deeper, at fullState.child.data — note the extra nesting, it trips up naive path code later when reconciling with patches (see below).
  • To confirm auth actually took, find your own record in players by id and check for a discordUserId field (older builds call it databaseUserId — accept either). A guest connection has neither.

Re-seed everything from a fresh Welcome on every reconnect, not just the first connect — the command sequence counter, and any local cache derived from full state. A reconnect is a brand-new server-side session even if your clientDocumentId stayed the same.

08PartialState & JSON Patch

After Welcome, state updates arrive as small patch lists rather than full re-sends: 

{
  "type": "PartialState",
  "patches": [
    { "path": "/data/players/0/coins", "value": 1250 },
    { "path": "/child/data/userSlots/0/data/garden/12/slots/0", "op": "remove" }
  ]
}

Applying one is a restricted JSON Pointer (RFC 6902-ish) operation:

  1. Split path on /, dropping the empty leading segment.
  2. If the path starts with /child, strip that prefix and apply against your game state tree; otherwise apply against your room state tree.
  3. If the first remaining segment is literally data, drop it too — both trees are rooted one level below their own data key, mirroring the shape fullState itself uses.
  4. Walk the remaining segments, creating an object or array at each level as needed (an array when the next segment is numeric, an object otherwise).
  5. At the leaf: op:"remove" deletes that key/index; anything else sets value at that key, extending an array with nulls if the index is past its current end.

RoomFrame messages carry the identical patch array one level deeper, at msg.state.patches. The simplest correct handling is to rewrite an incoming RoomFrame into a PartialState shape at the door and never special-case it anywhere else in your pipeline. 

typescripttype Patch = { path: string; value?: unknown; op?: "remove" };

function applyPatch(root: any, patch: Patch): any {
  let segs = patch.path.split("/").slice(1);
  if (segs[0] === "data") segs = segs.slice(1);
  if (!segs.length) return patch.value ?? root;

  let node = root;
  for (let i = 0; i < segs.length - 1; i++) {
    const key = segs[i], nextKey = segs[i + 1];
    if (node[key] === undefined) node[key] = /^\d+$/.test(nextKey) ? [] : {};
    node = node[key];
  }
  const leaf = segs[segs.length - 1];
  if (patch.op === "remove") {
    if (Array.isArray(node)) node.splice(Number(leaf), 1);
    else delete node[leaf];
  } else {
    node[leaf] = patch.value;
  }
  return root;
}

Two concrete sub-trees worth knowing by path, since almost everything you'll want to watch lives under one of them:

  • userSlots[i].data.activityLogs — the ability/event log for player slot i. Watching this is how mods surface "your pet just triggered an ability" notifications: diff the array length, and for each new entry check action against the game's known ability-name list and read parameters.pet for who did it.
  • userSlots[i].data.garden — that player's dirt tiles, each with a slots array of planted crops.

09QuinoaCommandResult

The server's acknowledgment (or rejection) of a wrapped command:

{ "type": "QuinoaCommandResult", "ok": true }
// or, on failure:
{ "type": "QuinoaCommandResult", "ok": false, "code": "invalid_sequence", "commandType": "HarvestCrop" }

Known code values on a rejection:

CodeCause
invalid_messageThe envelope was malformed — usually a command type sent flat that needed wrapping, or a missing required field.
invalid_sequencecommandSequence wasn't exactly frontier+1 — a duplicate, a gap, or (in a shared-socket userscript) a second sender racing yours.
no_slotNo free slot for what the command was trying to create/place (e.g. inventory or storage full).
rate_limitedSent too many of that command too quickly.
not_ackableYou wrapped a type the server still expects flat — the mirror image of sending a command type flat. The fix runs both directions: if wrapping a type starts coming back invalid_message, try sending it flat instead, and vice versa.
handler_errorThe server's own handler threw partway through. Distinct from every code above: the mutation may or may not have applied — treat this as a genuinely unknown outcome, not a confirmed failure, and never blindly retry it.

A silently-failed action and a rejected one look the same to a naive client — neither undoes anything visible. Always listen for this message type and surface ok:false somewhere (a debug log at minimum); it's the only signal that a command you sent was ignored.

A subtler failure mode than an explicit rejection: a command that gets no result message at all. If a later RoomFrame/PartialState reports an executedCommandSequence higher than the one you sent, and you still have no result for it, the server silently dropped that specific send — a real, distinct outcome from both success and an explicit rejection, worth tracking separately if you're building anything that retries on failure (never retry a genuinely unknown outcome, only a confirmed-dropped one).

11Two ways to read state

The socket isn't the only source of truth once you're running inside the actual page (i.e. you're a browser userscript, not a standalone client). A second, entirely separate path exists through the game's own React/jotai state — and some things are only reachable that way, because they're pure UI state that never touches the wire at all (which modal dialog is open, whether the camera is in a scripted "cinematic" cutscene).

12Reading the game's own atoms

The game's React tree uses jotai for state. jotai keeps a private WeakMap-like cache mapping atom-config objects to their live atom instances, but the game exposes an atom-cache-like object on the page anyway (used for hot-reload bookkeeping) — and it's a plain object with a .get(key, initial) method, or a plain Map, so it can be wrapped from outside without touching any private field.

The trick: wrap that cache's get, and every atom that flows through it gets inspected once as it's registered. From there you can:

  • Recognize specific atoms by matching a substring of their internal debug label (e.g. anything ending in /activeModalStateAtom) — labels are far more stable across builds than the object identity or the minified variable name that held the atom.
  • Capture a reference to that atom's write function so you can call it later, exactly like the game's own UI would.
  • For an atom with no getter at all (some are write-only from the outside), infer its current value by wrapping write and recording whatever gets written through it, since your wrapped copy stays in sync with every write the same way state.get would.
typescripttype JotaiAtom = { write?: (get: any, set: any, ...args: any[]) => any };

let activeModalStateAtom: JotaiAtom | null = null;
let gameAtomSet: ((atom: JotaiAtom, value: unknown) => unknown) | null = null;

function inspectAtom(key: unknown, atom: JotaiAtom): JotaiAtom {
  const label = String(key);
  if (label.endsWith("/activeModalStateAtom")) activeModalStateAtom = atom;

  if (gameAtomSet || typeof atom?.write !== "function") return atom;
  const original = atom.write;
  atom.write = function (this: JotaiAtom, get, set, ...args) {
    // Capture jotai's own `set` closure the first time ANY atom write fires,
    // then immediately restore every wrapped atom to its original writer —
    // this hook only needs to fire once, globally.
    gameAtomSet = (target, value) => set(target, value);
    atom.write = original;
    return original.call(this, get, set, ...args);
  };
  return atom;
}

function installAtomCacheHook() {
  const existing = (window as any).jotaiAtomCache;
  const cache = existing instanceof Map ? existing : existing?.cache ?? new Map();
  (window as any).jotaiAtomCache = {
    cache,
    get(key: unknown, initial: JotaiAtom) {
      const atom = cache.get(key) ?? initial;
      if (!cache.has(key)) cache.set(key, atom);
      return inspectAtom(key, atom);
    },
  };
}

// Later, anywhere, opening the seed shop exactly like clicking its own button would:
function openSeedShop() {
  if (!activeModalStateAtom || !gameAtomSet) return; // atoms not registered yet
  gameAtomSet(activeModalStateAtom, "seedShop");
}

Do not write to activeModalStateAtom directly (atom.write = ... assignment isn't the same as calling it) — jotai atoms created with a derived write function (atom(get => get(sourceAtom))) throw "write is not a function" if you try to set them as if they were plain writable atoms. Always resolve to the real writable source atom and call it through jotai's own set, captured exactly as shown above.

13Finding the renderer

The game renders through Pixi.js. Two independent global hooks exist specifically for devtools/inspection and are stable across versions because they're a public part of Pixi itself, not something the game added:

  • window.__PIXI_APP_INIT__(app) — called once with the Application instance, if the game constructed one.
  • window.__PIXI_RENDERER_INIT__(renderer, pixiVersion) — called once (or again, if the renderer is ever recreated — e.g. after a WebGL context loss from being backgrounded) with the raw Renderer.

Overwrite both with your own function that records the value and then calls through to whatever was there before (devtools may have hooked the same globals first). Not every build constructs a full Application — if only the renderer fires, synthesize a minimal app-like object around it ({ renderer, stage: renderer.lastObjectRendered, ticker }) so the rest of your code doesn't need two separate code paths.

Neither hook gives you the actual constructors (Text, Sprite, Graphics, ...) — Pixi isn't usually exposed as a global on the page. Get them by walking the live stage and duck-typing real display objects already in it, then reading .constructor off of one: 

typescriptinterface PixiCtors { Container: any; Sprite: any; Texture: any; Rectangle: any; Text: any; }

function findNode(root: any, pred: (n: any) => boolean, limit = 25_000): any {
  const stack = [root], seen = new WeakSet();
  let n = 0;
  while (stack.length && n++ < limit) {
    const node = stack.pop();
    if (!node || seen.has(node)) continue;
    seen.add(node);
    if (pred(node)) return node;
    if (Array.isArray(node.children)) stack.push(...node.children);
  }
  return null;
}

function getCtors(stage: any): PixiCtors | null {
  // A real Sprite: has a texture, whose frame is itself a real object.
  const sprite = findNode(stage, (x) => x?.texture?.frame && x.texture.constructor && x.texture.frame.constructor);
  if (!sprite) return null; // stage not populated yet — retry next frame

  // A real Text node: has `.text` + `.style`, and Pixi v8 tags it renderPipeId:"text".
  // The renderPipeId check matters — the game's Rive-based nodes also expose text+style
  // and would otherwise get misidentified, and Rive's constructor throws on Pixi-style args.
  const isRiveLike = (x: any) => !!(x?.artboard || x?.stateMachine || x?.rive);
  const looksLikeText = (x: any) => (typeof x?.text === "string" || typeof x?.text === "number") && x?.style;
  const text =
    findNode(stage, (x) => looksLikeText(x) && x.renderPipeId === "text") ??
    findNode(stage, (x) => looksLikeText(x) && !isRiveLike(x));
  if (!text) return null; // no text rendered yet — retry; don't cache a null Text ctor

  return {
    Container: stage.constructor,
    Sprite: sprite.constructor,
    Texture: sprite.texture.constructor,
    Rectangle: sprite.texture.frame.constructor,
    Text: text.constructor,
  };
}

Sprites render before any UI text does on a cold load, so a naive "found a sprite → done" check locks in Text: null permanently if it runs too early — poll on requestAnimationFrame and only accept the result once both a sprite and a genuine text node have been found in the same pass.

A separate constructor you'll also want — Graphics, for drawing your own shapes — isn't reliably duck-typeable by field shape the same way, but its methods are: the public roundRect()/clear() API is stable and unminified, so find any node exposing both and read its constructor: 

const graphicsCtor = findNode(stage, (n) => typeof n?.roundRect === "function" && typeof n?.clear === "function")?.constructor ?? null;

Cache every constructor at module scope once found — they're stable class references for the rest of the page session. Re-deriving them on every UI update means re-walking the entire stage (which, for the world/tile layer alone, can be tens of thousands of nodes) on every tooltip open, which is a measurable frame hit.

14Drawing text

Once you have a Text constructor and a target container to attach to, drawing text is exactly the public Pixi.js v8 API — nothing game-specific about the call itself, only about finding where to put it: 

typescriptconst style = { fontFamily: "Arial", fontSize: 14, fontWeight: "700", fill: "#FFD84D" };
const label = new ctors.Text({ text: "1,250", style });
label.position.set(0, 0);
targetContainer.addChild(label);

// updating it later is just an assignment — no re-creation needed:
label.text = "1,900";

The actual work is finding targetContainer — a real node already in the game's own scene graph, so your text moves, scales, and gets clipped exactly the way the game's own labels do. The game tags many of its Pixi containers with a plain-string .label property (not a minified identifier — these read like "GardenInfoCardSystem", "GardenInfoObjectCard"), which is by far the most stable hook point across builds. 

typescriptfunction findByLabel(root: any, label: string): any {
  return findNode(root, (n) => n.label === label);
}

// The card the game shows for whatever crop/egg/decor the player is looking at:
const cardSystem = findByLabel(stage, "GardenInfoCardSystem");

// Rather than re-searching on every frame, listen for the game's own `childAdded`
// event on that container — it fires exactly when a new card is shown:
cardSystem.on("childAdded", (row: any) => {
  if (row.label !== "GardenInfoCardRow") return;
  const card = findByLabel(row, "GardenInfoObjectCard");
  if (!card) return;
  attachValueLabel(card, ctors);
  card.once("destroyed", () => { /* the card is gone, clean up your own children */ });
});

Anything running inside a handler for one of the game's own scene-graph events (like childAdded above) executes synchronously inside the game's own render/update loop. If your handler throws, the exception bubbles up into the game's own rebuild and aborts it partway through — symptom: the whole card visibly shifts or renders half-built, not a clean crash. Wrap the entire body in try/catch and fail silently (log, don't rethrow).

Positioning text against an existing card reliably means anchoring to a stable reference point, not the card's rendered bounds — a large/fully-grown crop's icon can visually overflow the card's nominal box and throw off anything anchored to getBounds(). Prefer the card's fixed hitArea dimensions, or a specific labeled child row within it (e.g. a title row), over the whole card's bounding box.

15Text on Rive-animated objects

Not everything on screen is a Pixi display object. Pets and some decor are Rive animations — a separate runtime with its own artboards and state machines, composited into the same canvas but not reachable through ctors.Text at all. Rive has its own, much simpler surface for this: a named text run baked into the artboard by whoever authored it in the Rive editor, settable at runtime with one call. 

typescript// `artboard` here is a live Rive artboard instance — captured the same way
// you'd capture a Pixi app: hook Rive's own instantiation entry point once,
// record every instance that gets created, and look it up later by whichever
// asset name / tag you attached to it at capture time.
try {
  artboard.setTextRunValue("CoinLabel", "1,250");
} catch {
  // the artboard simply has no text run by that name — not every pet/decor
  // asset defines one, so treat a throw here as "unsupported", not a bug
}

There is no equivalent of addChild here — you can only set the value of a run the original asset already defines, not add a brand-new piece of text to an artboard that never had one. If you need arbitrary new text on top of a Rive-animated object (a pet, say), the practical answer is still the Pixi approach from the previous section: find the Pixi container that hosts the Rive canvas/texture and attach a Text node to that, positioned over it, rather than trying to inject a run into the artboard itself.

The same pattern extends past text: Rive artboards also expose named inputs (booleans, numbers, triggers driving the state machine) settable the same way, which is how a mod can force a specific animation state or swap a bound image without touching Pixi at all — outside the scope of "drawing", but worth knowing the surface exists if a feature calls for driving a pet's animation directly rather than just labeling it.

16Drawing shapes & badges

Use the Graphics constructor you found earlier the same way you'd use Pixi's public API — roundRect().fill() for a simple rounded badge behind a text label, which is the standard way to make custom text legible over arbitrary game art without needing to resize anything the game itself drew: 

typescriptconst badge = new graphicsCtor();
card.addChild(badge); // add once; redraw in place on every update

function redrawBadge(width: number, height: number) {
  badge.clear();
  badge.roundRect(0, 0, width, height, 6).fill({ color: 0x000000, alpha: 0.55 });
}

clear() then redraw is the correct update pattern — Graphics instances are meant to be reused across frames, not recreated. Recreating one every update leaks nodes and is measurably slower for anything updating more than a couple of times a second.

A full pattern for a value badge that tracks a moving game object, combining everything above:

typescript — condensed from a working modfunction attachValueLabel(card: any, ctors: PixiCtors) {
  const text = new ctors.Text({ text: "—", style: { fontFamily: "Arial", fontSize: 14, fill: "#FFD84D" } });
  const badge = new graphicsCtor();
  card.addChild(badge); // badge behind...
  card.addChild(text);  // ...text in front

  function sync(coins: number) {
    try {
      text.text = coins.toLocaleString();
      const pad = 8;
      badge.clear();
      badge.roundRect(-pad, -4, text.width + pad * 2, text.height + 8, 6)
           .fill({ color: 0x000000, alpha: 0.55 });
    } catch (err) {
      // never let this throw back into the game's own render loop
      console.warn("[my-mod] badge sync failed", err);
    }
  }

  return { sync, destroy() { badge.destroy(); text.destroy(); } };
}

18Building a world overlay (mini-games, custom scenery)

Drawing something into the actual farm world — not a UI overlay, but new scenery or a mini-game that temporarily takes over the player's own tiles — needs a few more pieces working together, all reusable across however many such features you build:

  1. A dedicated draw layer per z-band. Create one Graphics or Container per named layer (e.g. "background", "foreground"), each with its own zIndex, added as a child of the game's own world container. The farm sits near zIndex: 0, so background scenery needs a large negative index.
  2. A RenderLayer for anything drawn above the player avatar. Pixi's RenderLayer lets you sort a set of objects into a separate pass that composites above everything else, which is the only reliable way to draw in front of the player character — a raw large positive zIndex on the world container does not reliably beat the avatar's own sorting.
  3. Suppress the game's own tile redraw while your scene owns the space, and hide (don't destroy) the tiles/effects underneath so they can be restored byte-for-byte on exit.
  4. Claim "cinematic mode" (the same jotai atom from the state section) while active, so the game's own camera/input logic gets out of your way, and release your claim — not force it off — on exit, in case something else also claimed it.
  5. Herd active pets out of the affected tiles for the duration, and let them back in on exit.

19Multi-mod collisions

If you're a userscript sharing the page (and the socket) with the real game client — and potentially with other userscripts too — the command-sequence counter described earlier becomes a genuine coordination problem, not just bookkeeping. The game keeps its own module-private counter with no idea your script exists; the instant you send one command, both counters have silently claimed the same next number for different things.

Two independently-developed, compatible-in-spirit fixes:

Renumber everything on the way out

Patch WebSocket.prototype.send. While you've sent nothing yet, stay a passive observer: watch the game's own commandSequence values go by and track the highest one seen. The moment you inject a command, you own the counter from then on — rewrite every subsequent outgoing envelope, including the game's own, to the next number from your counter before it hits the wire. One chooser, no collisions, and every byte is untouched vanilla behavior until the first time you actually act.

Anchor to the server's own frontier

Rather than trusting a local counter at all, read the server's own confirmed executedCommandSequence directly off the room connection object (or scrape it out of incoming frames as a fallback) before stamping every outgoing command. If the server has already run past your next number — because a second script renumbered independently — jump forward to frontier+1. If a command comes back rejected as invalid_sequence, resync down to frontier+1 immediately. This survives a second mod doing its own renumbering on the same socket: a desync costs at most the one command that tripped it, not every command after.

The concrete, load-bearing lesson here for a userscript's own command-envelope sender: never assume you're the only writer on the socket. If you patch send, patch it once, detect your own previously-built envelopes (a request-id set you populate yourself) so you don't re-intercept or re-number your own outgoing traffic, and treat everything else passing through as a foreign frame that might need renumbering.

A third refinement: brand your own wrapper

Beyond renumbering, there's a coordination problem one level up: if your script re-installs its hook (a reconnect, a feature toggling on and off), how do you tell "my own wrapper is still installed, leave it" apart from "a wrapper is installed, but it's someone else's, or a stale one of mine from before a page navigation"? Tag every function you install with a private marker, and check for your own marker — not just "is something installed" — before deciding whether to wrap again: 

typescriptfunction brandWrapper<T extends object>(fn: T, label: string): T {
  (fn as any).__myModWrapped = true;
  (fn as any).__myModLabel = label;
  return fn;
}

function classifySlot(obj: object, key: string): "clean" | "mine" | "foreign" {
  if (!Object.prototype.hasOwnProperty.call(obj, key)) return "clean"; // nothing installed at all
  const value = (obj as any)[key];
  if (typeof value !== "function") return "clean";
  return value.__myModWrapped ? "mine" : "foreign"; // unrecognized wrapper = assume foreign, never claim it
}

Pair this with an identity-guarded restore: when tearing your hook down, only put the original function back if the slot still holds exactly the wrapper you installed. If some other script wrapped your wrapper in the meantime (layering its own hook on top of yours, which is completely legitimate), blindly restoring your captured "original" would silently erase that other script's hook too — a bug that only shows up as "the other mod's feature randomly stops working after mine unloads," which is a brutal one to trace back to its cause. 

typescriptfunction restoreSlot(obj: object, key: string, original: Function, installedRef: Function): boolean {
  if ((obj as any)[key] !== installedRef) return false; // someone wrapped ours after us — leave it alone
  (obj as any)[key] = original;
  return true;
}

20Sources & disclaimer

Everything above was reconstructed by reading the public source of three independent community projects, cross-checking where they overlap, and calling out where they don't:

  • Ariedam64/MG-AriesMod — browser userscript; primary source for the Pixi rendering material and the send-hook renumbering approach.
  • Liam0306dis/garden-companion — browser userscript; primary source for the jotai atom-cache approach and the frontier-anchored sequencer.
  • Ariedam64/mg-afk-android — native Android client with no browser or game code involved at all; the cleanest, least-ambiguous source for the raw wire format, since it has to reimplement the protocol from nothing rather than piggyback on the game's own client.
  • mg-tokyo/QPM-GR — "Quinoa Pet Manager," by far the largest of the four; primary source for the MagicCircle_RoomConnection object, the extended QuinoaCommandResult error codes, the wrapper-branding coexistence technique, and the Rive text-run material.
  • Ariedam64/Magic-Garden-API — an unofficial REST/asset service that mirrors game data (sprites, pet/plant metadata) for other tools to consume. It doesn't talk to the room protocol above and isn't the subject of this guide, but if you need static game data rather than live room state, it's a maintained source for that.

This is not official documentation, and none of it is guaranteed to still be accurate the moment the developers ship a client update — several sections above note exactly this (the flat/wrapped migration, the PartialState/RoomFrame transition). Treat every concrete field name and message shape here as "true as of the client builds these three projects target," and re-verify against current mod source before depending on it for anything that matters.

Compiled by reading source, not by asking the developers — because as of this writing, no official documentation for this API exists to ask about.
